# Rencana Porting Skema OtomaX 4.3.1 → PostgreSQL

**Tanggal:** 2026-10-17 | **Peran:** arsitek database (porting SQL Server → PostgreSQL)
**Metode:** forge — evidence-based. Setiap klaim bertipe diberi label:
- **[B]** = terbukti (nama/urutan kolom dari SP/view/grid di SCHEMA_DEEPDIVE.md)
- **[I]** = inferensi (tipe data ditebak dari pola nama & sampel data; belum terverifikasi)
- **[R]** = rekonstruksi (objek/kolom tidak ada di backup, dibangun dari referensi kode)

**Keputusan desain (dari EDISI_DAN_BATASAN.md):** tanpa batasan edisi, setara Ultimate, tanpa lisensi.
Implikasi DB: **tidak ada** kolom/tabel terkait lisensi yang perlu direplikasi; tidak ada kuota yang perlu dienforce di skema.

**Batasan sumber:** tidak ada satu pun `CREATE TABLE` di backup — semua tipe di bawah adalah
best-effort. Lihat §7 untuk mitigasi (cara mendapatkan DDL eksak).

---

## 1. Prinsip mapping tipe SQL Server → PostgreSQL

| SQL Server (asumsi) | PostgreSQL | Catatan |
|---|---|---|
| `INT IDENTITY(1,1)` | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | **BY DEFAULT** (bukan ALWAYS): SP sync melakukan insert `kode` eksplisit; PG menolak itu pada `ALWAYS` kecuali `OVERRIDING SYSTEM VALUE` |
| `DATETIME` / `GETDATE()` | `TIMESTAMPTZ`, default `now()` | Server pulsa lintas zona waktu; `timestamptz` aman untuk `waktu > now() - interval '4 days'` |
| `MONEY` / `DECIMAL` | `NUMERIC(19,2)` | Rupiah praktis tanpa sen, tapi pertahankan 2 desimal untuk harga_beli agregat |
| `BIT` | `BOOLEAN` | Kolom flag grid (`aktif`, `gangguan`, `kosong`, `fisik`) |
| `VARCHAR/NVARCHAR` kode | `TEXT` | Hindari batas panjang artifisial; kode reseller `OR0001`, kode produk `VSTID45` |
| `VARCHAR(MAX)` pesan | `TEXT` | `inbox.pesan`, `outbox`, format balasan |
| `TINYINT/SMALLINT` status | `SMALLINT` | `ItemStatus` 49 nilai muat di smallint |

**Aturan identifier:** semua nama tabel/kolom di bukti sudah lowercase (`transaksi`, `kode_reseller`).
Di PG, identifier tak dikutip dilipat ke lowercase — cocok 1:1. **Data-access layer harus memakai
nama lowercase persis** (atau selalu quoted). Ini keputusan arsitektur, bukan opsional.

**Case sensitivity (risiko, lihat §7):** SQL Server default collation case-insensitive.
Kolom kunci string (`reseller.kode`, `oto_user.nomor`) disarankan memakai ekstensi `CITEXT`
agar perilaku `WHERE kode='or0001'` tetap cocok. DDL di bawah memakai `TEXT` + catatan;
keputusan CITEXT vs TEXT diambil saat porting DAL (satu baris `CREATE EXTENSION`).

---

-- [B] definisi view. Hardcoded range kode 445863–448361 adalah artefak sample DB
-- → dijadikan FUNCTION berparameter agar berguna operasional.
CREATE OR REPLACE FUNCTION cek_stok(p_kode_modul INT, p_nominal NUMERIC,
                                    p_kode_min INT DEFAULT NULL, p_kode_max INT DEFAULT NULL)
RETURNS TABLE (kode INT, tgl_entri TIMESTAMPTZ, kode_produk TEXT, tujuan TEXT, pesan TEXT)
LANGUAGE sql STABLE AS $$
    SELECT t.kode, t.tgl_entri, t.kode_produk, t.tujuan, i.pesan
    FROM transaksi t
    LEFT JOIN inbox i ON i.kode = t.kode_jawaban
    JOIN produk p ON p.kode = t.kode_produk
    WHERE t.kode_modul = p_kode_modul
      AND t.status = 20                    -- Sukses [B]
      AND p.nominal = p_nominal
      AND (p_kode_min IS NULL OR t.kode BETWEEN p_kode_min AND p_kode_max);
$$;
-- Komentar: pemakaian asli: cek_stok(81, 50, 445863, 448361)

-- [B] definisi view harga_agen.
CREATE OR REPLACE VIEW harga_agen AS
SELECT o.nama AS operator, p.kode, p.harga_jual + 200 AS harga
FROM produk p
JOIN operator o ON o.kode = p.kode_operator
WHERE p.aktif = TRUE
  AND p.kode NOT LIKE 'S50P'
  AND p.kode NOT LIKE '%H'
  AND p.kode NOT LIKE '%F'
  AND p.kode NOT LIKE 'FT%'
  AND p.kode NOT LIKE 'FK%'
  AND p.kode NOT LIKE 'HF%'
  AND p.kode NOT LIKE 'Z%'
  AND p.kode NOT LIKE 'M%'
  AND p.kode NOT LIKE 'IN%'
  AND p.kode NOT SIMILAR TO 'A[^X]%';
-- Catatan: pola 'A[^X]%' adalah T-SQL LIKE class; di PG menjadi SIMILAR TO. [B] pola dari sumber.

    kode_reseller     TEXT NOT NULL,
    kode_dompet       TEXT NOT NULL,
    saldo             NUMERIC(19,2) NOT NULL DEFAULT 0,
    tgl_update        TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT pk_reseller_saldo PRIMARY KEY (kode_reseller, kode_dompet),
    CONSTRAINT fk_reseller_saldo_reseller FOREIGN KEY (kode_reseller) REFERENCES reseller(kode),
    CONSTRAINT fk_reseller_saldo_dompet   FOREIGN KEY (kode_dompet)   REFERENCES dompet(kode)
);
-- reseller.saldo dipertahankan sebagai saldo dompet utama ('1') untuk kompatibilitas
-- semua path potong-saldo existing; engine mengupdate keduanya atomik dalam 1 transaksi.

## 3. Konversi stored procedure & trigger → PL/pgSQL

> Kejujuran metode: source T-SQL lengkap hilang bersama `/tmp/bak-strings.txt`
> (tmpfs). Konversi di bawah adalah **rekonstruksi setia dari ringkasan logika
> SCHEMA_DEEPDIVE.md §3** — struktur benar, detail eksak (nama variabel, kondisi
> batas) perlu verifikasi ulang saat porting DAL.

### 3.1 `AddKomisiTunda(@trxid, @kodereseller, @jumlah)` → upsert komisi

```sql
-- Perilaku asli: INSERT jika belum ada baris (kode_transaksi, kode_reseller),
-- UPDATE (tambah jumlah) jika sudah ada. Dipicu saat SettingTundaKomisi=1.
CREATE OR REPLACE FUNCTION add_komisi_tunda(p_trxid INT, p_kodereseller TEXT, p_jumlah NUMERIC)
RETURNS VOID LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO komisi (kode_transaksi, kode_reseller, jumlah)
    VALUES (p_trxid, p_kodereseller, p_jumlah)
    ON CONFLICT (kode_transaksi, kode_reseller)
    DO UPDATE SET jumlah = komisi.jumlah + EXCLUDED.jumlah;
END;
$$;
-- Catatan: ON CONFLICT adalah padanan idiomatis PG untuk pola IF EXISTS UPDATE ELSE INSERT di T-SQL.
-- Jika semantik aslinya REPLACE (bukan akumulasi), ganti menjadi: DO UPDATE SET jumlah = EXCLUDED.jumlah.
```

Penarikan komisi (`TUKAR.[jumlah].[pin]` / `TUKAR`) adalah logika aplikasi: kurangi `komisi`,
tambah `mutasi` + `reseller.saldo`. Tidak ada SP-nya di bukti — diimplementasikan di engine.

### 3.2 `DownloadFromMaster` → sync inkremental (sketsa setia)

Fungsi asli: sinkronisasi DB live → database backup `otomax_bak` (fitur online backup).
Di arsitektur baru, pola yang benar adalah **postgres_fdw** (baca DB live sebagai foreign table)
atau mengganti fitur ini dengan `pg_basebackup`/`pg_dump` terjadwal. Sketsa di bawah memakai
dblink/fdw secara konseptual; nama tabel remote diberi prefix `live_`.

```sql
-- Pseudo-PL/pgSQL (rekonstruksi dari SCHEMA_DEEPDIVE.md §3):
CREATE OR REPLACE FUNCTION download_from_master() RETURNS VOID LANGUAGE plpgsql AS $$
BEGIN
    -- 1. reseller: update saldo+tgl_aktivitas yang berubah; insert kode baru
    --    (butuh kolom pembanding; aslinya membandingkan saldo & tgl_aktivitas)
    UPDATE reseller r SET saldo = l.saldo, tgl_aktivitas = l.tgl_aktivitas
    FROM live_reseller l WHERE l.kode = r.kode
      AND (l.saldo IS DISTINCT FROM r.saldo OR l.tgl_aktivitas IS DISTINCT FROM r.tgl_aktivitas);
    INSERT INTO reseller SELECT * FROM live_reseller l
    WHERE NOT EXISTS (SELECT 1 FROM reseller r WHERE r.kode = l.kode);
    -- ON CONFLICT DO NOTHING tidak dipakai karena perlu UPDATE selektif di atas.

    -- 2. oto_user: upsert by nomor (kode_produk, nama_produk, imsi, serial_number, tgl_status)
    INSERT INTO oto_user AS o ...
    ON CONFLICT (nomor) DO UPDATE SET ...;  -- ringkas; kolom sesuai §2.2

    -- 3. oto_histori / oto_histori_update: insert watermark
    INSERT INTO oto_histori (tgl_proses)
    SELECT tgl_proses FROM live_oto_histori WHERE tgl_proses > (SELECT max(tgl_proses) FROM oto_histori);
    -- (pola sama untuk oto_histori_update dengan tgl_update)

    -- 4. transaksi: update baris yg di backup status<20 tapi di live status>0
    --    (kolom: status, kode_modul, tgl_status, kode_jawaban, sn); insert kode > max(kode)
    --    → butuh OVERRIDING SYSTEM VALUE karena kode adalah IDENTITY:
    INSERT INTO transaksi (...) SELECT ... FROM live_transaksi
    WHERE kode > (SELECT max(kode) FROM transaksi)
    -- ditulis dengan daftar kolom eksplisit + OVERRIDING SYSTEM VALUE;

    -- 5. tiket_deposit: update status untuk tiket 4 hari terakhir yg masih 'O' tapi live sudah berubah;
    --    insert baru. (waktu > now() - interval '4 days', padanan GETDATE()-4)
    -- 6. mutasi, data_bank: insert by max(kode) (pola sama dengan transaksi).

    -- 7. Cleanup: hapus mutasi & inbox milik reseller yang sudah tidak ada
    DELETE FROM mutasi WHERE kode_reseller IN
        (SELECT kode_reseller FROM mutasi EXCEPT SELECT kode FROM reseller);
    DELETE FROM inbox WHERE kode_reseller IS NOT NULL AND kode_reseller NOT IN
        (SELECT kode FROM reseller);
    -- Catatan: aslinya memakai temp table #rsmati (reseller mati). Jika definisi
    -- #rsmati ditemukan saat porting DAL, ganti dengan CTE/TEMP TABLE PG.
END;
$$;
```

**Rekomendasi arsitektur:** fitur "online backup" ini di clone sebaiknya **tidak** dipertahankan
sebagai sync baris-per-baris. Ganti dengan `pg_basebackup` + WAL archiving (PITR) atau
`pg_dump` terjadwal — lebih andal dan tidak butuh logika diff manual. Fungsi di atas hanya
diperlukan bila kompatibilitas perilaku 1:1 diminta.

### 3.3 Trigger `tr_oto_user_data`

```sql
-- Asli (T-SQL): AFTER UPDATE → UPDATE oto_user SET tgl_data=GETDATE() WHERE nomor = ...
-- Terjemahan idiomatis PG: BEFORE UPDATE (menghindari trigger rekursif).
CREATE OR REPLACE FUNCTION trg_oto_user_data_fn()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    NEW.tgl_data := now();
    RETURN NEW;
END;
$$;

CREATE TRIGGER tr_oto_user_data
BEFORE UPDATE OF kode_produk, nama_produk, imsi, serial_number, tgl_status
ON oto_user
FOR EACH ROW
EXECUTE FUNCTION trg_oto_user_data_fn();
-- Catatan: daftar kolom OF (...) opsional; tanpa OF = setiap UPDATE. Pilih sesuai kebutuhan audit.
```

### Keputusan arsitektural: multi-dompet penuh (P0 #10 — FINAL, 2026-10-17)

**Keputusan: MULTI-DOMPET PENUH** (bukan single-dompet). Alasan:

1. **Bukti fitur kuat [B].** Edisi eWallet OtomaX adalah edisi multi-dompet; format transaksi
   membawa `kodedompet` yang divalidasi engine (Version.txt:94, :110, :194); halaman Mutasi punya
   filter Kode Dompet (Version.txt:28); tabel Dompet punya kolom Regex Pengirim, Parameter Balasan,
   Refund Ke (Version.txt:44, :58, :82). Keputusan desain "setara Ultimate, tanpa lisensi" (§6)
   berarti SEMUA fitur edisi dibuka — multi-dompet wajib didukung skema, bukan dipangkas.
2. **Biaya salah pilih asimetris.** Menambah `kode_dompet` ke `mutasi`/`transaksi` SEKARANG =
   murah (instalasi baru; `NOT NULL DEFAULT '1'` membuat semua kode single-dompet lama jalan
   tanpa perubahan). Retrofit SETELAH produksi = backfill jutaan baris mutasi + rewrite semua
   query saldo + risiko downtime. P0 #10 memperingatkan persis ini ("salah pilih = migrasi mahal").
3. **Kompleksitas query terkendali.** Satu kolom `kode_dompet` di `mutasi` dan `transaksi`:
   saldo per-dompet = filter biasa (`WHERE kode_dompet='2'`); total semua dompet = `SUM` tanpa
   filter. Index `ix_mutasi_dompet(kode_reseller, kode_dompet)` menutup pola akses utama.
4. **Kebutuhan bisnis nyata.** Server pulsa memisahkan dompet pulsa vs e-wallet vs deposit;
   refund routing per dompet (`dompet.refund_ke`, '.' = dompet asal [B]) tidak bisa dimodelkan
   bersih dengan single-dompet.
5. **Kompatibilitas mundur terjaga.** `dompet` seed `'1' = Dompet Utama`; `reseller.saldo`
   dipertahankan sebagai saldo dompet utama agar semua path potong-saldo existing (locking
   `SELECT ... FOR UPDATE`, refund, laporan) tidak berubah; saldo per-dompet dimaterialisasi
   di `reseller_saldo`, diupdate engine atomik bersama `reseller.saldo` dalam 1 transaksi.

**Dampak skema (sudah diterapkan di DDL):** `dompet` (§2.7); `mutasi.kode_dompet NOT NULL
DEFAULT '1'` + FK + index (§2.1); `transaksi.kode_dompet NOT NULL DEFAULT '1'` + FK (§2.1);
`reseller_saldo(kode_reseller, kode_dompet)` (§2.8). Alternatif yang DITOLAK: single-dompet
dengan `kode_dompet` nullable — menghemat satu tabel hari ini dengan harga migrasi mahal
dan refund-per-dompet yang tidak termodelkan.

## 5. Strategi migrasi & seeding (instalasi baru)

### 5.1 Urutan eksekusi DDL
1. `CREATE EXTENSION IF NOT EXISTS citext;` (opsional, lihat §1) + `pg_trgm` (untuk pencarian `LIKE '%...%'` di `tujuan`/`pesan`) + **`CREATE TYPE jenis_mutasi`** [R] (§2.1 — type harus ada sebelum tabel `mutasi`) + **`CREATE SEQUENCE seq_angka_unik_tiket;`** [R] (generator angka unik tiket deposit — harus ada sebelum `tiket_deposit` agar `DEFAULT nextval('seq_angka_unik_tiket')` valid).
2. Tabel tanpa FK: `operator`, `hlr`, `level` (self-ref: buat dulu tanpa FK, lalu `ALTER TABLE ADD CONSTRAINT`), `modul`, `dompet`, `grup_reseller`, `peran`, `pengirim`, `daftar_hitam`, `auto_respon`, `oto_user`, `oto_histori`, `oto_histori_update`, `setting`.
3. Tabel dengan FK: `reseller` (→`level`, →`grup_reseller`; self-ref `kode_upline` via ALTER) → `provider` → `produk` → `pengguna` (→`peran`) → `peran_menu` (→`peran`) → `parsing` → `inbox` → `terminal` → `outbox` → `transaksi` (→`dompet`) → `tiket_deposit` (→`dompet`; pasang `ALTER TABLE tiket_deposit ALTER COLUMN angka_unik SET DEFAULT nextval('seq_angka_unik_tiket');` setelah sequence dibuat) → `data_bank` → `mutasi` (→`dompet`) → `komisi` → `voucher` → `harga_grup` → `markup_produk` → `mutasi_poin` → `mutasi_unit` → `hadiah_poin` → `monitor_saldo` → `saldo_snapshot_harian` → `data_bank_riwayat` → `transaksi_histori` → `reseller_saldo` (→`reseller`, `dompet`).
   Catatan: `transaksi.kode_voucher` SENGAJA tanpa FK (hindari siklus DDL dengan `voucher`; link otoritatif = `voucher.kode_transaksi`).
4. View `harga_agen`, function `cek_stok`, function `add_komisi_tunda`, trigger `tr_oto_user_data`, lalu ALTER FK self-ref (`level.kode_upline`, `reseller.kode_upline`).
5. Verifikasi: `\d` tiap tabel + `SELECT` smoke test.

### 5.2 Seeding minimal agar engine bisa jalan
1. **Modul**: 15 kanal TipeModul (kode numerik dipetakan saat porting; sementara 1–15); `parameter='{}'` default.
2. **Dompet**: 1 baris `('1', 'Dompet Utama')` [R]; dompet tambahan (e-wallet) dibuat via UI.
3. **Level**: 1 baris default (mis. `LVL1`).
4. **Grup Reseller**: 1 baris default (mis. `GRP1`) [R]; reseller admin memakai grup ini.
5. **Operator**: dari daftar produk sampel (Telkomsel/XL/Axis/tri/by.U/PLN…).
6. **HLR/Provider**: minimal 1 baris agar validasi prefix tidak gagal.
7. **Reseller admin**: 1 akun induk (`OR0001`) + saldo awal; engine membuat baris `reseller_saldo` untuk dompet '1' saat pendaftaran [R].
8. **RBAC**: 4 peran bawaan [R — diselaraskan dengan arch_engine.md §12; konvensi lowercase]: `admin` (semua), `operator` (transaksi + monitor + aksi operasional), `teknisi` (modul/terminal/setting), `kasir-kiosk` (layar kasir saja); 1 baris `pengguna` admin (kata sandi di-set saat instalasi, simpan hash argon2/bcrypt — jangan plaintext); `peran_menu`: admin = semua menu `boleh_ubah=true`, kasir-kiosk = minimal (layar kasir), operator/teknisi = sesuai haknya.
9. **Setting**: key-value dasar (`SettingTundaKomisi=0`, format balasan default, dsb. — nilai default dari perilaku app, bukan dari bukti).

### 5.3 Jika migrasi dari SQL Server live (punya DB produksi)
1. **Opsi A (disarankan bila butuh DDL eksak):** restore `db_otomax.bak` ke SQL Server 2022 Express (gratis, jalan di Linux via container) → *Generate Scripts* → jadikan acuan koreksi tipe di §2. Ini menutup gap tipe terbesar dengan biaya kecil.
2. **Opsi B:** `pgloader` langsung dari SQL Server → PG (menangani IDENTITY→identity, datetime→timestamptz otomatis).
3. Pasca-load: `SELECT setval(pg_get_serial_sequence('transaksi','kode'), max(kode))` untuk tiap identity agar insert berikutnya tidak tabrakan.

### 5.4 Konvensi operasional
- Backup: `pg_dump` harian + WAL archiving (menggantikan `DownloadFromMaster`).
- Cleanup reseller mati dijalankan sebagai job terjadwal (dulu di akhir SP; jadikan cron/pg_cron).

## 7. Risiko & ketidakpastian utama

| # | Risiko | Dampak | Mitigasi |
|---|---|---|---|
| 1 | **Tipe data kolom tidak pasti** (tanpa CREATE TABLE) | Bug runtime saat porting DAL (overflow, truncation, konversi gagal) | Opsi A §5.3 (restore .bak ke Express, generate DDL eksak) — mitigasi termurah & paling pasti |
| 2 | **Kolom tak terpetakan** di `oto_user/reseller/inbox/oto_histori` | Query INSERT/SELECT app gagal (kolom hilang) | Skema evolutif + migration tool (rekomendasi: `golang-migrate`/`dbmate`); lengkapi saat porting DAL |
| 3 | **Case sensitivity**: SQL Server CI vs PG case-sensitive | Login/lookup reseller & nomor gagal bila case beda | `CITEXT` untuk kolom kunci string, atau normalisasi `lower()` di DAL |
| 4 | **IDENTITY + insert eksplisit** (sync) | `duplicate key` bila sequence tidak di-reseat pasca bulk load | Selalu `setval()` setelah COPY/pgloader; pakai `GENERATED BY DEFAULT` (§1) |
| 5 | **Semantik `GETDATE()` vs `now()`** | Beda zona waktu bila server tidak UTC | Set `timezone='UTC'` di server; app kirim/tampilkan dalam WIB di lapisan presentasi |
| 6 | **Temp table `#rsmati`** di SP asli | Logika cleanup reseller-mati hilang | Rekonstruksi saat porting §3.2 dari kebutuhan (definisi "reseller mati" dari kode app) |
| 7 | **Presisi uang** (`MONEY` vs `NUMERIC(19,2)`) | Selisih rounding di agregat komisi | `NUMERIC(19,2)` + uji rekonsiliasi agregat vs SQL Server |
| 8 | **Pola `LIKE 'A[^X]%'`** | Salah tafsir bila diterjemahkan mentah ke `LIKE` PG | Sudah diterjemahkan ke `SIMILAR TO 'A[^X]%'` di view (§2.6); uji dengan data |
| 9 | **View `cek_stok` hardcoded** | Di PG dijadikan function — pemanggil lama (laporan) harus diubah | Ubah pemanggil ke `cek_stok(modul, nominal, min, max)` |
| 10 | **Tabel setting tak terpetakan** | Konfigurasi app (format SMS, pola param) tak punya rumah | Tabel `setting` key-value baru (§4 #8); nilai default dari perilaku, bukan bukti |

**Risiko terbesar tunggal:** #1 (tipe data). Semua DDL §2 adalah best-effort; satu putaran
verifikasi melawan DDL eksak (Opsi A §5.3) atau melawan runtime DAL akan memakan sebagian
besar waktu fase DB. Anggaran realistis: DDL awal 1–2 hari, hardening tipe 3–5 hari iteratif.
